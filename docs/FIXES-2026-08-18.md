# Fix batch — first real-machine test

Seven findings from the first end-to-end test on a real machine. Five are bugs,
one is a UX failure, one is not our bug.

---

## F1: Settings window is blank and its edits do nothing

**Confirmed root cause.** `tkinter` variables bind to an interpreter, not a
widget. A `tk.StringVar(value=...)` created without a `master` attaches to
`tkinter._default_root` — the **first** `Tk()` created in the process. In the
running app that is `app.py`'s hidden pump root, while the settings widgets
live in the settings window's own `Tk()`. Different interpreters, so the Entry
looks up a variable name that does not exist there and renders empty.

Reproduced directly:

```
variable's interpreter is the hidden root: True
entry showing a master-less var : ''
entry showing a mastered var    : '-12.0'
```

It is worse than cosmetic. `var.get()` still reads the *other* interpreter's
value, so ticking "Show popups" changes a checkbox that is not wired to the
variable being saved — the edit silently does not take.

Not data-destroying: `_save` guards numeric fields with `try/except ValueError`,
so blank strings leave values unchanged, and `_coerce` catches the empty
strings that reach string fields.

**Fix.** Pass `master=` to every Tk variable in the codebase.

**Regression test.** Mechanically enforced by AST inspection, in the same
spirit as `tests/test_boundaries.py`: scan every module for `StringVar`,
`BooleanVar`, `IntVar`, `DoubleVar` construction and assert each passes a
`master` argument. A unit test of one window would not stop the next one
reintroducing it.

## F2: The microphone list is unusable

19 entries for about 5 physical devices. PortAudio enumerates every device once
per host API, so one headset appears under MME, DirectSound *and* WASAPI. The
list also contains things that are not microphones at all (`PC Speaker`,
`Primary Sound Capture Driver`) and raw driver strings
(`Input (@System32\drivers\bthhfenum.sys,#2;%1 Hands-Free%0...)`).

**Fix.** A pure function in `stfu/audio.py`:

```python
def preferred_input_devices(devices) -> list[InputDevice]
```

- Drop host-API aliases and non-capture endpoints: names beginning
  `Microsoft Sound Mapper`, `Primary Sound Capture Driver`, `PC Speaker`, and
  raw driver strings (containing `@System32\` or `;%1`)
- Group the rest by device name, keeping one entry per physical device
- Prefer host APIs in the order **WASAPI → DirectSound → MME → WDM-KS**
  (WASAPI is the modern shared-mode path and the lowest latency of the four)
- Preserve enumeration order otherwise, so the list is stable between runs

The wizard shows the filtered list. The full list stays available via
`list_input_devices()` and `stfu.cli devices`, because a filter that hides the
one device someone needs is worse than a long list.

## F3: "Recalibrate" opens Settings

It opens the settings window, where recalibration is a button. It should start
the calibration flow directly.

**Fix.** Extract the calibration dialog from `SettingsWindow._recalibrate` into
its own `CalibrationDialog` class in `stfu/calibrationui.py`, and have both the
tray item and the settings button open it.

## F4: The PIN prompt needs Enter

`simpledialog.askstring` requires Enter or OK.

**Fix.** A small custom dialog that **verifies on each keystroke and closes as
soon as the PIN is correct**. Enter and an OK button stay, for a wrong PIN or
for anyone who prefers them.

This leaks the PIN length to an observer watching the dialog close. That is
irrelevant here: the PIN is documented as a speed bump, not a lock, and anyone
with admin rights can end the process anyway.

## F5: A second yell was not detected

Almost certainly the **30-second cooldown** working as designed — one yell can
not chain into several punishments. But "is it even listening?" is a fair
question that the app currently gives no way to answer.

**Fix.** A **live meter** window, opened from the tray with no PIN, showing:

- the current level in dBFS, updating continuously
- the threshold in force
- a bar, so it is obvious at a glance whether input is arriving at all
- the seconds remaining on the cooldown, so a suppressed yell is visibly
  suppressed rather than apparently ignored

That last line is the point. Without it, a working cooldown and a dead
microphone look identical.

## F6: Mouse lag while the microphone is open

**Not caused by this app**, and the user sees it with Teams too. It is a
well-known Windows behaviour: opening a capture stream raises DPC latency in
some audio driver stacks, and Intel Smart Sound Technology — present on this
machine — is a common culprit.

**What we can do.** The capture stream currently forces `samplerate=16000`. The
device almost certainly runs at 44100 or 48000 natively, so Windows inserts a
resampler on every buffer. Loudness does not care about sample rate: RMS is
RMS. Opening at the device's default rate removes a resampling step from the
audio path.

**Fix.** Open `MicSource` at the device's default sample rate and derive the
frame size from it, keeping the 20 ms frame duration the detector expects.

This may or may not help the lag — it is one contributing factor among several,
and the honest expectation is "worth doing anyway, might not fix it".

## F7: The app icon is PyInstaller's default

**Fix.** Generate a proper icon at build time with Pillow — a speaker with a
mute slash, drawn at 16/32/48/64/128/256 px so it stays legible in the taskbar
and the title bar. Apply it to the exe via the spec and to every Tk window via
`iconphoto`.

The tray icon keeps its coloured state circles (green listening, amber paused,
grey no mic) — those carry information the app icon cannot.
